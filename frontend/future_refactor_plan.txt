# Refactor StudyPage.jsx

The `StudyPage.jsx` component has grown to nearly 3,000 lines of code. It currently handles UI layout, API fetching, heavy simulation logic, complex state management, and contains hardcoded algorithm configurations.

## Proposed Architecture Changes

I propose breaking down this massive monolith into a modular directory structure under `src/pages/Study/` and extracting utility functions and hardcoded data into separate files.

### 1. Extract Hardcoded Data & Logic
- **`src/utils/studyConstants.js`**: Move `PSEUDOCODE_MAP`, `getPseudocodeLines`, `getPracticeTemplate`, and `getComplexityString` out of the component.
- **`src/utils/simulationEngine.js`**: Extract the massive `useEffect` block (lines 560-890) that generates simulation steps for `binary-search`, `linear-search`, etc., into pure functions (e.g., `generateBinarySearchSteps(array, target)`). This will make the simulation logic testable and decoupled from React state.

### 2. Component Sub-division
We will create a new directory `src/pages/Study/` to replace the single file:

- **`index.jsx` (Container)**: Will manage only the top-level state (like `activeTab`, `selectedLesson`, data fetching) and render the layout grid.
- **`Sidebar.jsx`**: Handles the course navigation tree and search.
- **`RightSidebar.jsx`**: Handles the AI Tutor chat, notes, and related widgets.
- **`Tabs/` Directory**:
  - `OverviewTab.jsx`
  - `VisualSimulatorTab.jsx` (will handle its own playback state `isPlaying`, `playSpeed`, `simStepIndex`)
  - `CodeSandboxTab.jsx`
  - `QuizTab.jsx`
  - `PracticeTab.jsx`

## Future Considerations for Scalability

When scaling to 2,000+ topics, hardcoding simulation logic in the frontend is not maintainable. We will need to transition the simulation engine to be fully dynamic using one of these approaches:
1. **Database-Driven Configuration**: Store simulation rules, pseudocode, and state-change logic as JSON inside the MongoDB `Lesson` schema. The frontend becomes a "dumb" player that just reads these rules from the backend.
2. **Auto-Tracer (WASM)**: Store actual source code in the database and use a lightweight WebAssembly compiler in the browser to run the code and automatically trace variable changes (similar to PythonTutor).
